# PIVNIK Android kiosk — сохранение подписи и безопасные обновления

## Подтверждённое состояние

Реальное kiosk-устройство уже успешно обновлялось **поверх установленного приложения**, без удаления и factory reset. Поэтому считать прежний ключ потерянным или требовать сброс устройства **нельзя**. Рабочую signing identity необходимо сохранить. Этот документ не содержит секретов и сам по себе не разрешает деплой Draft PR #165.

Существующая Android-сборка в PR #165 использует debug-keystore, который восстанавливается из GitHub Actions cache. При потере кэша workflow может **создать новый ключ**. Новый сертификат не является продолжением существующей цепочки обновлений; такой APK нельзя выдавать за совместимый с установленным kiosk.

## P0: установить и сохранить действующую signing identity

1. Зафиксировать package name установленного приложения (`ru.pivnik.kiosk`) и отпечаток SHA-256 сертификата **реально установленной версии**. `adb shell dumpsys package ru.pivnik.kiosk` помогает проверить пакет, но не является надёжным способом извлечь сертификат на каждой версии Android. Для сравнения сертификатов использовать исходный установленный APK или штатный Android PackageManager/аппаратную проверку, а также `apksigner`.
2. Проверить SHA-256 сертификата APK, которым **уже успешно обновили** устройство, и подтвердить совпадение с установленной версией.
3. Найти фактически использованный keystore и alias. **Не генерировать замену.**
4. Создать минимум **2–3 независимые защищённые резервные копии** keystore и реквизитов восстановления. CI-кэш не считается резервной копией; одна учётная запись/одно устройство не считаются независимыми хранилищами.
5. Проверить восстановление одной резервной копии и возможность подписать ею тестовый APK с тем же сертификатом.
6. Зафиксировать в защищённом операционном журнале владельца расположение резервных копий и ответственного. В GitHub разрешено фиксировать только не-секретные fingerprint, инструкцию восстановления и статус проверки.

### Проверка кандидата (только чтение)

```sh
apksigner verify --print-certs app-debug.apk
keytool -list -v -keystore /secure/path/existing.keystore -alias EXISTING_ALIAS
```

Не публиковать keystore, пароли или вывод, содержащий секреты, в PR, CI-логах или issue.

## Безопасная целевая схема CI

После подтверждения **именно действующего** ключа CI должен получать его из защищённого хранилища (например, Actions secrets), а не генерировать новый при cache miss. Настроить fail-closed проверку **ожидаемого SHA-256 сертификата** готового APK перед выдачей артефакта. В PR #165 `app/build.gradle` поддерживает `KIOSK_RELEASE_STORE_FILE`, `KIOSK_RELEASE_STORE_PASSWORD`, `KIOSK_RELEASE_KEY_ALIAS`, `KIOSK_RELEASE_KEY_PASSWORD`; переменные нельзя заполнять случайно созданным ключом.

Рекомендуемые секреты CI: `KIOSK_RELEASE_KEYSTORE_B64`, `KIOSK_RELEASE_STORE_PASSWORD`, `KIOSK_RELEASE_KEY_ALIAS`, `KIOSK_RELEASE_KEY_PASSWORD`, `KIOSK_RELEASE_CERT_SHA256`. Отпечаток сравнивать после нормализации регистра и разделителей. Если ключ/ожидаемый отпечаток недоступны или не совпадают — **сборка для выпуска останавливается**, без fallback на debug/new key.

## Gate перед следующим обновлением реального kiosk

- Кандидат собран из согласованного коммита, не из непроверенной Draft-ветки.
- Подпись кандидата совместима с подписью установленного приложения; версия `versionCode` допускает обновление.
- Подтверждены 2–3 независимые копии **действующего** keystore и проверено восстановление.
- Android unit/build checks и репозиторные проверки пройдены; на контролируемом устройстве проверено обновление поверх без потери Device Owner, Lock Task, pairing, PIN, VK, Telegram и VPN.
- Только после этого можно планировать отдельный выпуск на kiosk в баре. **Никакого автоматического factory reset, смены подписи или установки APK из Draft PR #165.**
