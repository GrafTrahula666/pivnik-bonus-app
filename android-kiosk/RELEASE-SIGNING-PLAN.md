# План постоянного ключа подписи Android kiosk

Этот документ — release gate. Он не создаёт ключ и не разрешает устанавливать APK из draft-веток на реальное устройство.

## Текущее подтверждённое состояние

Установленный kiosk (versionCode 1) подписан сертификатом с SHA-256, начинающимся с `28EBAE22` и заканчивающимся `F40E`. Сам приватный ключ в репозитории не хранится.

Пока исходный keystore не найден и его сертификат не сверён с установленным APK, существующее устройство нельзя считать безопасно обновляемым новым APK.

## Вариант A — сначала восстановить существующий ключ

1. Найти исходный `.jks` / `.keystore` на компьютерах, резервных дисках, в менеджере паролей и других контролируемых хранилищах владельца.
2. Ничего не загружать в репозиторий.
3. Проверить сертификат найденного keystore:

```
keytool -list -v -keystore <path-to-keystore> -alias <alias>
```

4. Сверить полный SHA-256 с сертификатом установленного приложения. Для APK:

```
apksigner verify --print-certs app-release.apk
```

5. Только при полном совпадении использовать этот keystore для будущих release-сборок.

## Вариант B — если старый ключ действительно утрачен

Переход на новый постоянный ключ означает, что APK с ним не обновит установленное приложение поверх. Для реального kiosk потребуется отдельно запланированная переустановка / повторная настройка Device Owner. Не делать это автоматически из CI или draft PR.

Создать новый ключ один раз на доверенном компьютере владельца:

```
keytool -genkeypair -v -keystore pivnik-kiosk-release.jks -alias pivnik-kiosk ^
  -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=Pivnik Kiosk, O=Pivnik, C=RU"
```

Пароли — длинные случайные, хранить в менеджере паролей.

## Хранение — минимум 3 независимые копии

1. Менеджер паролей владельца: `.jks` + store password + key password + alias.
2. Зашифрованный офлайн-носитель в отдельном физическом месте.
3. GitHub Actions secrets для CI.

CI-кэш не является резервной копией ключа.

## GitHub Actions secrets

| Secret | Значение |
|---|---|
| `KIOSK_RELEASE_KEYSTORE_B64` | base64 содержимое `.jks` |
| `KIOSK_RELEASE_STORE_PASSWORD` | пароль хранилища |
| `KIOSK_RELEASE_KEY_ALIAS` | alias ключа |
| `KIOSK_RELEASE_KEY_PASSWORD` | пароль ключа |
| `KIOSK_RELEASE_CERT_SHA256` | полный ожидаемый SHA-256 сертификата |

## Release gate в CI

`app/build.gradle` должен получать release signing credentials только из переменных окружения / secrets. Release-сборка обязана завершаться ошибкой, если credentials отсутствуют или SHA-256 сертификата APK не совпадает с `KIOSK_RELEASE_CERT_SHA256`.

Пример проверки:

```
echo "$KIOSK_RELEASE_KEYSTORE_B64" | base64 -d > "$RUNNER_TEMP/release.jks"
KIOSK_RELEASE_STORE_FILE="$RUNNER_TEMP/release.jks" gradle :app:testDebugUnitTest :app:assembleRelease
apksigner verify --print-certs app/build/outputs/apk/release/app-release.apk
rm -f "$RUNNER_TEMP/release.jks"
```

Сравнение SHA-256 должно быть машинно проверяемым и падать при несовпадении.

## Перед установкой на реальный kiosk

- PR с kiosk-кодом смержен и прошёл release gate.
- Release APK подписан постоянным ключом.
- Полный SHA-256 сертификата APK совпадает с ожидаемым.
- Если обновляем существующую установку — сертификат совпадает с установленным приложением.
- `versionCode` выше установленного.
- Есть отдельная резервная копия keystore вне CI.
- Установка draft APK на реальное устройство запрещена без отдельного явного решения о риске.

## После закрепления постоянного ключа

Записать сюда полный SHA-256 сертификата (публичный отпечаток, не секрет) и дату проверки. Раз в квартал проверять, что как минимум две резервные копии keystore открываются и дают тот же сертификат.
