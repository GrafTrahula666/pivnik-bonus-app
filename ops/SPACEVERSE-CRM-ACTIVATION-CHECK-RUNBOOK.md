# Проверка запуска отдельной SPACEVERSE CRM

Эта итерация добавляет сохраняемую **проверку возможности запуска**, а не активацию
платной CRM. Проверенного installation/subscription/revoke контракта Маркета ещё
нет. Ни успешная проверка схемы, ни сохранённый ответ кассы не включают заведение.

## Как продолжить подключение

1. В существующем мастере откройте сохранённое заведение. Подготовьте область,
   привязку выделенной базы и подтвердите её схему. Пустая база допустима;
   недоступная база не считается пустой.
2. В разделе «Запуск CRM» нажмите «Проверить запуск CRM». Отдельное гостевое
   приложение и его bundle/image для CRM-сайта не требуются.
3. Выполните указанное сервером действие: подготовка базы, исправление привязки,
   завершение схемы или проверка связи с кассой. Принадлежность данных другой
   точки нельзя исправлять автоматическим присвоением или backfill.
4. Состояние и число попыток сохраняются. После reload или потерянного ответа
   нажмите «Обновить состояние запуска». Повторный запуск доступен только по
   серверному `startAllowed`; браузер не вычисляет окончание lease.
5. Даже при свежей кассе состояние останется pending: установка и оплата
   Эвотор.Маркета пока не подтверждаются. Текст «CRM ещё не запущена» намеренный.

## Включение в изолированной среде

Новый флаг `ADMIN_ENABLE_TENANT_CRM_ACTIVATION_CHECKS=false` по умолчанию.
Также требуются существующие `ADMIN_ENABLE_WRITES` и
`ADMIN_ENABLE_ONBOARDING_DRAFTS`. Доступ — создатель с актуальными правами,
владелец компании (все её заведения) или приглашённый owner/manager выбранного
заведения. Владелец нескольких компаний работает со всеми своими магазинами.
Viewer и отозванный доступ не допускаются к запуску проверки. Управляющему не выдаются права
владельца компании.

Новая Admin migration `016_crm_activation_check.sql` применяется **только вручную**
после существующих миграций 004–015 через штатный защищённый migration workflow.
Автоматический startup её не запускает. Production migration, включение флагов,
секреты и реальные внешние действия в этой итерации не выполнялись.
Сначала проверяют актуальный backup/restore и разрешение на конкретную среду.
Не переписывать предыдущие миграции и не менять production users/wallets/purchases.

Защищённый target registry остаётся прежним. Новые URL или ключи в браузере
не принимаются. Включение нового флага требует валидной конфигурации реестра.
Для сохранённого подтверждения кассы нужны существующие workflow/POS proxy
флаги; закрытый device key должен оставаться расшифровываемым сервером.

## Реальный серверный контракт

- `GET /api/admin/onboarding/drafts/:draftId/crm/activation-check` читает состояние.
- `POST` по тому же URL с **ровно `{}`** запускает проверку.
- Query, scope, license, status, URL и credentials не принимаются.
- Существующие signed session, Origin и CSRF обязательны; общий для GET/POST
  лимит — 20 запросов в минуту на оператора.
- Ответ: `schemaVersion:1`, canonical `scope`, `operation` из существующего
  provisioning ledger, `activationStatus:pending|verifying|failed`,
  `activationAllowed:false`, `crmStatus:not_provisioned`,
  `guestApplicationRequired:false`, русская `nextAction`.
- `operation.step=crm_activation_check`; статусы `not_started`, `running`,
  `action_required`, `retryable_error`. `result` всегда null. Проверка не выдаёт
  список клиентов, баланс, секреты или текст ошибки драйвера.

В существующей таблице `admin_onboarding_provisioning_steps` хранится одна строка
этого шага на frozen draft/venue. Применяются прежние source matching, lease/token,
reclaim и счётчик попыток. Нового tenant identity, registry, invitation или
subscription ledger нет. SQL constraint миграции 016 запрещает `succeeded` именно
для этого шага; даже случайный application write не может сохранить успех.

Dependency — прежний `tenant_schema_readiness`, без runtime bundle/image.
Каждый запуск заново выполняет настоящую проверку exact binding, требуемых
столбцов/constraints/indexes и ownership всех данных в target PostgreSQL:
`REPEATABLE READ READ ONLY`, statement timeout 5 секунд. Никаких tenant writes,
миграций или денежных операций. Сохранённый schema success не заменяет эту проверку.

Target работа идёт вне metadata transaction. Перед завершением заново блокируются
активная учётная запись, актуальные grants, draft и строка операции в том же
порядке, что при claim. Проверяются frozen manifest, lease/token и фактическое
время lease; потерявший lease worker не перезаписывает более новую попытку.
Ошибка аудита откатывает результат. Неопределённая попытка остаётся running до
истечения lease, затем допускает повторную проверку без второй строки операции.
Это идемпотентность read-only проверки, не реализация financial idempotency.

После реальной проверки схемы сервер перечитывает сохранённое подтверждение POS
в metadata transaction и проверяет доступность расшифровки credentials. Использует
тот же freshness contract, что `/crm/readiness`: точные confirmed scope/terminal,
полный отчёт, свежие provider check и terminal event, отсутствие будущих timestamps.
Это **последнее сохранённое подтверждение**, не новый сетевой запрос к кассе.
Следующий блокер всегда подписка: synthetic proof не выдаётся за реальную оплату.

## Причины блокировки

| Код | Действие |
| --- | --- |
| `TARGET_DATABASE_NOT_REGISTERED` | Завершить защищённую регистрацию базы |
| `TARGET_DATABASE_UNAVAILABLE` | Проверить связь; состояние failed, данные не превращаются в нули |
| `TARGET_BINDING_CONFLICT` | Исправить серверную привязку; чужую БД не использовать |
| `TARGET_TENANT_SCHEMA_REQUIRED` | Подготовить схему вручную, без автоматических migrations |
| `TARGET_TENANT_DATA_OWNERSHIP_REQUIRED` | Разобраться с принадлежностью данных, без автоматического усыновления |
| `CRM_PROVIDER_VERIFICATION_REQUIRED` | Отправить тестовое событие и повторить существующую проверку связи |
| `CRM_MARKET_CONTRACT_REQUIRED` | Подключить и реально проверить будущий Market adapter |

## Что ещё требуется для активации

Актуальная спецификация Маркета и тестовое приложение, installation/payment/revoke
проверки, доверенное evidence подписки и его срок/отзыв, атомарная canonical
активация, отдельный resolver активной CRM, отзыв доступа на каждом запросе и E2E
полного платного сценария. Новый шаг не ослабляет prepared source guard и не
меняет `companies.active`/`venues.active`. Прежние активные заведения не выключаются.
Готовность к продаже и публикации этим PR не заявляется.

## Список заведений: сохранённая проверка CRM

В списке «Заведения» сразу видно, почему CRM ещё не запущена, сколько было
попыток и когда сохранено состояние. «Продолжить подключение» открывает тот же
мастер. «Обновить заведения» перечитывает сохранённые данные, не запускает новую
проверку и не подключается к клиентской базе или кассе. Сохранённый результат
явно подписан как прошлый; он не является свежим подтверждением связи/оплаты.
Отсутствие предыдущей проверки отличается от недоступного состояния: во втором
случае число попыток неизвестно, а не равно нулю. Истёкшая проверка требует
повтора. Если есть более серьёзная текущая ошибка кассы, она остаётся основным
действием; сохранённый результат CRM виден отдельно. Для CRM-сайта наличие
bundle/image гостевого приложения не выбирает следующий шаг.

Это расширение существующего GET `/api/admin/onboarding/venues`: optional
`crmActivation` появляется только у draft при включённом прежнем флаге проверки
CRM. Поля: schemaVersion 1, draftId, scope, status/code/nextAction, attemptCount
(number или null), updatedAt, evidence (`not_checked`, `saved_activation_check`,
`unavailable`), crmStatus `not_provisioned`, activationAllowed false и
guestApplicationRequired false. Нет runtime key, manifest checksum, ключей,
клиентских данных и сумм. Company/venue по-прежнему определяются сервером.
Владелец видит и открывает все магазины всех принадлежащих ему компаний;
выбор конкретного магазина задаёт контекст операции и не отнимает доступ к остальным.
Наблюдатель с действующим приглашением читает только свою точку; endpoint
запуска и подробной проверки остаётся недоступным ему. Отзыв гранта между
выборкой списка и проекцией исключает draft из ответа.

Используется тот же ledger и source matcher. Чтение перед возвратом повторно
сверяет frozen manifest и текущий read grant. Ошибка чтения/несовпадение source
дают degraded/unavailable, без выдачи старого результата за подтверждённый.
Существующие active venues без draft сохраняют прежний unknown status. Флаг
выключен — прежний контракт списка, без чтения нового CRM step. Новых миграций
или настроек среды не требуется; production изменения этим описанием не делаются.
