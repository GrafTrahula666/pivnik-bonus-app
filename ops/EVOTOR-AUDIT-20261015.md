## Свежая сеть и уточнение симптомов

Первое сообщение владельца — «В базе данных не найден товар со штрихкодом
PIVNIK:…». Оно относится к товарному поиску Эвотора; по нему одному нельзя
доказать, что служба приложения не запускалась. Документация говорит, что POS
параллельно ищет товар. Возврат пустых позиций не является гарантией поглощения QR.

Затем владелец уточнил, что главный блок — подключение. Скрин 08:33 на кассе:
`SocketTimeoutException: timeout`, версия 1.0.8, «Не настроено», ожидаемый Railway
hostname. На скрине нет даты; окно журнала выбрано по времени получения скрина,
а не доказанной синхронизации часов терминала. Таймаут не объясняется отсутствием
ключа: достижимый POS API без ключа возвращает 401.

Railway прочитан через подключённые инструменты, без изменения конфигурации:

- deployment `19661129-1446-41ef-b42a-b68afd166632`, SUCCESS, main `3d3d193`,
  без staged changes;
- в HTTP-журнале с 13 октября — четыре контрольных POST resolve 14 октября,
  401 за 5–26 мс; успешного resolve кассы в этом окне нет, bind-запросов нет;
- с 15 октября 05:28 UTC (08:28 МСК) до проверки 05:33:56 UTC resolve-запросов
  не найдено; health в 08:30:32 МСК ответил контрольному probe 200 за 26–27 мс;
- существующая функция `evotor-sync-setup`, которую эта сессия не меняла,
  завершила чтение облака в 08:30:49 МСК: complete=true, last_error_code=null,
  документов в scoped store 41399. Это доказательство направления сервер→облако,
  а не работы касса→сервер. Функция импортирует документы; это не наша новая запись;
- независимый контрольный POST без ключа через Railway test endpoint ответил 401
  в 08:35:05 МСК за 28 мс; поздний повторный запрос журнала показывает только
  эту нашу строку `undici`, а не обращение кассы.
  Тестовые данные отклонены до поиска QR/записи. Он не прошёл через прокси Эвотора.

Нет коррелированного успешного запроса терминала. Отсутствие завершённой строки
HTTP-журнала не доказывает точный сетевой узел обрыва. Возможны конфигурация/применение
прокси, путь до облака, путь облака до Railway либо TLS/transport терминала.
Портал и логи облака недоступны; точная причина не объявлена установленной.
Запрошены фактические разрешённые URL и состояние ver.2.

Маски в портале — регулярные выражения: `/*` не эквивалентно `/.*`.
Три проверяемых пути: `/api/device/pos/qr/resolve`,
`/api/device/pos/receipts/bind`, `/api/health`. Нельзя считать старый пересказ
списка URL доказательством текущего списка.

## Блокеры и минимальный следующий шаг

P1: касса не получает ответ, ключ не настроен; полный сценарий не работает.
P1: списание в обеих APK отсутствует; починка сети сама по себе его не добавит.
P2: несовместимые подписи и неверное поглощение товарного QR.

Следующий шаг — сверить текущую proxy-конфигурацию с реальными путями, затем
сопоставить свежий тест кассы с HTTP-журналом. При подтверждённых верных настройках
нужен trace Эвотора за точное время: app_uuid, resolved destination IP,
reason/subject, стадия DNS/TCP/TLS/HTTP и upstream request ID. Не переустанавливать
приложение и не менять сервер ради непроверенной гипотезы.

Для полного начисления после восстановления связи: сохранить штатный ключ,
получить resolve и bind, закрыть один согласованный чек, сравнить SDK receipt UUID
с cloud document id и проверить единственную запись начисления и повторную доставку.
Списание требует отдельного законченного кассового протокола с реальной скидкой/
оплатой, серверным резервом, подтверждением закрытия, отменами и возвратами;
ручное изменение баланса без изменения расчёта чека не заменяет этот сценарий.

## Дополнение: разрешённая подготовка обновления 1.0.10

После отчёта владелец прямо разрешил выпуск обновления и уточнил, что связь
необходимо проверять без ввода ключа. В 1.0.10 это две отдельные кнопки:
keyless network check (ключ не читается и не отправляется в HTTP-запросе) и
проверка уже сохранённого ключа. Только собственный POS JSON-ответ 401 считается
подтверждением связи; произвольные 401/403 прокси не означают отказ ключа.
`BridgeSettings` и `DeviceCredentialStore` побайтово не менялись относительно main.

Локально после уточнения прошли 36/36 JVM core тестов, полные материализованные
Node тесты 545/545 и `npm run check`. Изменённые Android-классы проходят описанную
выше дополнительную интерфейсную проверку с адаптером. Gradle/SDK сборка и
совместимая публикация выполняются отдельным workflow, их результат нельзя
заменить этими локальными тестами.

Журнал именно сборки 1.0.8: GitHub run `38297682195`, source `70f77d7`,
job `114972623422`. Постоянный `EVOTOR_KEYSTORE_FILE` в окружении сборки отсутствовал;
android-keystore backup/cache шага нет, Gradle cache охватывал только `caches`.
Артефакты — APK и тестовый отчёт, без private keystore. В доступном workspace
`.jks`/`.keystore` не найдены. Это доказывает отсутствие доступной здесь копии,
но не глобальную утрату ключа у владельца/предыдущего сборщика.

Новый workflow сначала собирает unsigned release без генерации ключа. Публикация
требует полных EVOTOR signing secrets и сертификата ровно установленной 1.0.8
`3EE4BE58E006C0608BF36E1F9DFEDB5C69899F2335BA96AF94CAA2857FD4C953`.
Если ключа нет или он другой, публикация останавливается. Старые APK не заменяются,
force-push исключён. Появление unsigned артефакта не является выпуском обновления
для кассы. Терминал, портал Эвотора и production backend не изменяются этим workflow.

## Бюджет ответа прокси — 16.10.2026, 1.0.11/code15

На свежем снимке 1.0.10 повторён timeout на этапе ожидания ответа и в health.
В журнале backend соответствующих обращений кассы не найдено; независимый
контрольный POST без ключа вернул ожидаемый 401 за 33 мс. В Маркете прочитаны
назначение приложения одной кассе и статус «Установлено 1/1»; это не означает
проверенную передачу запросов с терминала. Точная причина обрыва не установлена.

Документация Эвотора задаёт шлюзу 5 секунд на соединение с внешним сервером и
10 секунд на получение данных. Read timeout клиента в 10 секунд мог завершать
проверку до ответа самого шлюза. В 1.0.11 для diagnose, health и resolve/bind
установлены connect=10s/read=30s. На ошибке показываются длительность ожидания и
issuer сертификата уже состоявшегося POST TLS-соединения; TLS validation и trust
store не менялись. Первое соединение закрывается перед health, health дополнительно
показывает ограниченное тело ошибки и существующий `ProxyDiagnostic` hint.
Название issuer с «Trust» не считается TLS-ошибкой: `SettingsActivity` анализирует
только первую строку исключения. Экран предупреждает об ожидании до 90 секунд.

Сертификат постоянной подписи сохранён, версия пакета повышена до 15. Совместимое
обновление поверх подписанной 1.0.10 не требует удаления приложения. Эта проверка
не доказывает исправленную связь или реальные бонусные операции; списание не
реализовано. Серверные маршруты, деньги, схема БД и signing secrets не менялись.
