# Целевая модель статусов мастера подключения заведения

Согласованный словарь для мастера. Серверная проекция уже реализована в
`admin-platform/server/onboarding-workflow.ts`, `GET/PUT .../progress` и UI
`OnboardingProgress.tsx`; ручная migration 012 сохраняет шаг/терминал/modules.
Источники прежние: canonical scope, application, provider и provisioning ledger.
Статусы не принимаются из браузера. Это ещё не подтверждение активного runtime
или живого терминала: они остаются pending/not_provisioned.

## Целевой сценарий мастера (из начала до конца)

1. **Организация** — название, тип, контакты. Соответствует уже существующему
   draft (`admin_onboarding_drafts`).
2. **Точка (заведение)** — адрес, часовой пояс, бренд приложения. Соответствует
   уже существующему app config + prepared scope (`admin_onboarding_app_config`,
   `prepareOnboardingScope`).
3. **Подключение кассы/провайдера** — на сегодня: Эвотор (уже есть защищённое
   хранение credential + read-only проверка документов, `onboarding-secrets.ts`,
   `pos/evotor-client.ts`). В будущем — другие провайдеры по тому же контракту.
4. **Привязка терминала** — ID/название сохраняются отдельно. Реальная привязка
   устройства и тестовое событие пока не подтверждаются, статус остаётся pending.
5. **Включение модулей** — бонусы, гости, рассылки и т.д., по аналогии с уже
   существующими `admin_company_access`/feature flags в Business.
6. **Проверка** — сквозная сверка того, что реально приходят данные (не только
   «подключено»), подтверждение tenant/runtime binding (уже есть частично в
   `onboarding-provisioning.ts`: resumable ledger, exact/reopen/replay).

## Статусы (единый словарь для владельца)

Каждый шаг (3–6 выше) должен уметь сообщить один из следующих статусов —
единообразно для всех провайдеров/модулей, а не произвольный текст:

- `not_configured` — шаг ещё не начат (ничего не сохранено).
- `pending` — данные сохранены (например, credential), но подключение ещё не
  проверялось или ожидает действия (например, первого чека с кассы).
- `verifying` — идёт активная проверка (запрос к провайдеру/терминалу в
  процессе, ответ ещё не получен или проверяется повторно).
- `active` — подтверждено и работает: данные реально приходят, последняя
  проверка успешна в разумном окне.
- `degraded` — было active, но последние проверки показывают проблему
  (устаревшие данные, частичные ошибки), без полного отказа.
- `suspended` — осознанно отключено владельцем/системой (например, временная
  приостановка точки), не ошибка.
- `failed` — проверка завершилась отказом (неверные credentials, провайдер
  недоступен дольше разумного времени, терминал не отвечает).

Переходы ограничены: из `not_configured` можно попасть только в `pending` или
`verifying`; `active`/`degraded`/`failed` достижимы только после хотя бы одной
реальной проверки (т.е. не из `not_configured` напрямую). `suspended` — ручной
переход из любого состояния кроме `not_configured`, с возвратом в `pending`
при возобновлении.

## Правило «0 ₽ не значит нет данных»

Нулевая выручка/ноль транзакций за период — это **данные** (касса подключена и
сообщает «ноль»), а не признак отсутствия связи. Статус не должен становиться
`failed`/`degraded` только потому, что сумма равна нулю. Деградация/отказ
определяются отдельно: по отсутствию самого факта связи (нет ответа, нет
heartbeat/последнего события дольше порога), а не по величине суммы. Это уже
частично соблюдается в `onboarding-secrets.ts`/`evotor-client.ts` (проверка не
основана на одном лишь HTTP 200 или факте наличия токена) — здесь фиксируется
как явное правило для будущего owner-facing статуса, чтобы не потерять его при
дальнейшей реализации.

## Соответствие уже существующему коду (на момент записи)

- Шаги 1–2 и частично 3 (Эвотор credential storage + read-only проверка) уже
  реализованы в PR #273.
- Серверная проекция показывает единые статусы восьми шагов, включая приложение
  и развёртывание. Свежая provider verification подтверждает чтение документов;
  через 15 минут её статус degraded и требуется новая проверка. Отказ после
  подтверждённого доступа отличается от первого отказа. Сумма в эти переходы
  не входит. Все выключенные выбранные модули имеют suspended.
- Общий статус не становится active из-за сохранённого blueprint/terminal ID,
  точной binding БД или documents_readable. Отчёт без сквозной связи содержит
  unavailable/null; настоящий пустой отчёт требуется отдельно подтвердить.
- Provisioning projection отдельно различает pending/error/success для binding,
  read-only schema readiness и runtime bundle. Проверенный bundle означает
  только совпадение manifest/checksum/контракта общего артефакта; он сохраняет
  `not_provisioned`, `published=false` и не считается запущенным runtime.
- Остаются proxy v2, разрешённый запуск tenant runtime, событие терминала и список
  заведений владельца; см. `ops/SPACEVERSE-ONBOARDING-PROGRESS.md`.
