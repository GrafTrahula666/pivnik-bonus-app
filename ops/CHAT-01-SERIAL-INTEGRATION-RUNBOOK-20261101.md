## Single-flight merge/release lock: required PROCESS (not implemented automation)

Before the first candidate, designate **one integration owner for that release window** with explicit authority. The lock is an operational protocol, **not an existing GitHub-enforced mutex**. Lock record required in release checkpoint:

- release_id, owner, acquired_at_utc, expires_at_utc, current_main_sha, candidate_pr + head_sha, changed paths + compatibility matrix, staging/production target service IDs;
- CI required status URL and decision, pre/post service deployment IDs+SHA, migration inventory, backup references (no secret values), rollback strategy, approval, postdeploy verification and close/abort reason.

### Acquire / merge / verify / release / unlock

1. **Acquire:** read latest main HEAD, open PRs and other chat checkpoints; verify no other integrator or workflow/operator has an active release/merge window; inspect Railway staged/BUILDING/DEPLOYING activity, service watch patterns, migrations and API consumers. If any unknown or concurrent release, **HOLD**. Announce sole candidate SHA; freeze all other merges/deploys, including docs. No current GitHub ruleset implements a global exclusive lock, so humans and agents must coordinate it explicitly.
2. **Pre-merge test:** on a fresh main-based candidate inspect diff and origin duplicate; complete materialize×2/idempotence, node --test, npm run check, npm audit, npm audit --omit=dev --audit-level=high, VK parity/bundle as relevant, Admin build/typecheck/Vitest/Playwright and native PostgreSQL scope/financial tests. Inspect root/server dual route parity, Do-not-break, tenant denial, POS locks and migration order. Required review and exact-head status must be successful. Do not assert green without tool output.
3. **Production safety gate:** obtain explicit owner authorization for that specific main merge and expected auto-deploy; check production backup availability and restoration **on disposable target**, exact SHA for all service deployments, rollback compatibility, active clients and that the current required main gate can authorize Railway. Documentation-only PRs still require this gate.
4. **Merge exactly one PR** only when all gates passed. Record resulting merge SHA (not just old PR head). **Do not merge another PR while CI/Railway are running**, even if they appear unrelated. No direct main push or automatic sweeping of Draft PRs.
5. **Check separate deploy paths:** GitHub main release gate including Railway read-check, explicit Telegram/VK releases and resulting SHA; independently read Railway auto-deployments (pivnik-bonus-app, pivnik-vk-test, admin-pilot). An Admin SKIPPED deployment means Admin remains on its previous SHA; do not claim it serves merged Admin code.
6. **Postrelease signed/offline/E2E checks:** health and release SHA, Telegram/VK login + identity separation, QR aliases, staff PIN and transactions, bonus accrual/redemption/idempotency, live Evotor cash/read-only consistency, Admin tenant RBAC including foreign venue/customer denial, time period/chart and mobile paths. Only run permitted non-destructive checks on real business. Observe errors/restarts and confirm producer/consumer API payload compatibility.
7. **Close or HOLD:** release owner publishes proof and moves to next PR **only after** completed known-good production state. If any verification missing/fails or version mismatch, freeze queue; enter incident/rollback decision. The lock remains until a clearly recorded resolution. The next chat's next step must resume from this precise checkpoint, not restart the queue.

## Rollback: distinguish deployment revision from data recovery

- **First response:** HOLD further merges, classify incident (HTTP/API, auth/tenant leak, POS money, service failed/partial deploy, schema/data). Preserve incident logs, exact main SHA, all service deployment IDs, no secret values.
- **App-only regression with backward-compatible DB:** if **explicitly approved** by owner and confirmed safe for installed clients, consider Railway rollback/redeploy of the last known-good service image independently for Telegram and VK, checking both identity/database fingerprint and release SHA again. Railway currently returns canRollback=true for their most recent successful deployment, **not** a guarantee that it will pass live tests. Admin has separate previous SUCCESS and may require its own rollback or leave-as-is decision.
- **Partial service release:** a successful Telegram deploy and failed VK/Admin deploy is **NOT** a successful release. Verify cross-service session schema, terms version, DB fingerprint and API consumers before rolling forward/back; do not apply an arbitrary previous SHA to a shared schema.
- **Schema/migration or money inconsistency:** do not auto-run down migrations, drop data, undo financial transactions or restore production databases. Root ops/backup-postgres.sh creates a checksum-verified pg_dump custom-format backup (when actually executed), but **NO backup was performed in this task**; no backup existence is inferred from the script.
- **Important destructive restore guard:** ops/restore-postgres.sh uses **pg_restore --clean --if-exists**, gated by CONFIRM_RESTORE. This is a potentially destructive restore process, **not a safe one-button production rollback**. It requires a separate owner-approved recovery plan, verified latest backup, disposable restore test, impact on writes made since backup, DB identity and data-loss analysis. Do not invoke it automatically.
- **Kiosk signing/Android:** never treat Railway code rollback as APK/signature rollback. Verify installed certificate and pre-existing same-key APK update plan. No factory reset or new keystore without special approval.
- **Recovery exit:** after mitigation, recheck every affected service's deployed SHA, Railway health/readiness, real critical paths and data reconciliation; record incident/mitigation and only then release lock.
