# Подключение Эвотора в баре «Пивник»

Подготовлено 02.10.2026. Это инструкция для отдельного согласованного подключения
после ревью и merge. В этой задаче касса, production и рабочая БД не менялись.

## Что подключаем

Читаем закрытые документы SELL и PAYBACK из REST API Облака V2. Продажа гостю
без приложения попадает в общую аналитику без создания профиля. Ручной журнал
Пивника остаётся самостоятельным источником и явно подписан. Его суммы не
складываются с кассовыми суммами.

Два раздела существующей админки: «Клиенты приложения» и «Все продажи кассы».
Дни и часы — Europe/Moscow; свой период включает обе выбранные даты.
Статистика клиентов содержит только явно подтверждённые покупки, а не совпадения
имени, телефона, суммы или времени. Импорт не начисляет/списывает бонусы.

**Модель:** на чеке ранее подтверждён Эвотор. Эвотор 10 / ST1010 — предположение
по фотографии; нужна наклейка. Модель и кассовое ПО ещё не проверены.

## Что нужно получить одним списком

1. Фото наклейки модели и экрана с версией кассового ПО.
2. Адрес кабинета владельца и номер телефона, на который он зарегистрирован;
   названия установленных интеграционных приложений и их тарифы. Пароль не присылать.
3. Подтверждение доступа к dev.evotor.ru или возможность создать кабинет разработчика.
4. После разрешённой установки: API-токен и ID магазина через защищённые серверные
   настройки; один обезличенный JSON продажи и возврата для сверки реальной схемы.

## Внешние условия до выезда

| Где | Действие | Результат |
|---|---|---|
| Удалённо, кабинет разработчика | Создать облачное приложение для чтения документов, без APK для первого этапа | Черновик приложения |
| Удалённо, вкладка «Интеграция» | Включить «Получать документы из облака Эвотор»; создать вкладку «Настройки», текстовое поле со значением `${token}` | Разрешение читать документы и способ получить токен вручную |
| Кабинет разработчика | Вкладка «Тестирование»: добавить телефон владельца, затем «Версии» → «Выложить на тест» | Приложение видно тестировщику |
| Владелец, market.evotor.ru | Войти под добавленным телефоном, открыть страницу приложения и проверить условия установки | Установленное приложение и доступ к его настройкам |
| Владелец + Эвотор | Подтвердить условия теста, постоянную тарификацию и процедуру ревью/публикации | Согласованный способ постоянного подключения |

Облачный API не требует разработки APK для загрузки общих продаж. Но это не
отмена требований Эвотора к установке/активации приложения на нужных терминалах:
ответ 402 требует проверки всех касс магазина, установки и оплаты. Ничего
платного автоматически не подключать. В опубликованной документации тарифы
называются ориентировочными и согласуются отдельно; заказной доступ к API также
может тарифицироваться. Тестирование не заменяет разрешение на постоянную работу.
Публичная публикация требует процедуры ревью. Если нужные функции/переключатели
в кабинете отсутствуют — уточнить у поддержки Эвотора, не включать лишние права
на изменение товаров/остатков. Используем только GET.

Токен вручную: кабинет владельца → «Мои приложения» → наше приложение →
«Настройки» → поле токена. Пароль от кабинета API-токеном не является.
OAuth и автоматическая доставка токена не включены в этот минимальный этап.
Входящих вебхуков нет: неподписанные/неавторизованные события не принимаются.

## Серверные настройки без секретных значений

| Переменная | Назначение |
|---|---|
| `PIVNIK_POS_ENABLED` | `false` по умолчанию; `true` только при согласованной активации |
| `EVOTOR_API_TOKEN` | Секретный токен пары приложение–владелец; только сервер/worker |
| `EVOTOR_STORE_ID` | ID именно магазина «Пивник», полученный через GET /stores |
| `DATABASE_URL` | Существующая БД нужного окружения; во время подготовки — только тестовая |
| `NODE_EXTRA_CA_CERTS` | При необходимости доверенный корневой сертификат УЦ Эвотор из официальной документации; не отключать TLS-проверку |
| `PGSSLMODE` | Для отдельного worker `disable` только в доверенной внутренней сети; по умолчанию TLS с проверкой сертификата |

Не передавать токен через браузер, URL, git, скриншот или журнал. Не логировать
тело API-ошибки. При перевыпуске токена заменить секрет в обоих серверных
процессах/worker и повторить синхронизацию. Использовать секреты выбранного окружения.

## Удалённая подготовка перед подключением (после отдельного разрешения)

1. Review → merge → тестовый деплой. Нельзя считать эту draft-ветку production-релизом.
2. В тестовой копии БД выполнить `migrations/012_evotor_sales.sql`. Эта миграция
   исключена из автоматического startup-списка; создаёт только три POS-таблицы.
   Production-миграция — отдельное согласованное действие с резервной копией.
3. Получить список магазинов: серверный GET `https://api.evotor.ru/stores`
   с `Authorization: Bearer <секрет>` и `Accept: application/vnd.evotor.v2+json`.
   Использовать клиент с секретом из защищённого окружения, без вывода заголовков.
   Выбрать магазин по его данным в кабинете, не по догадке.
4. Проверить GET `/stores/{store-id}/documents?type=SELL,PAYBACK`, без `since`
   для первой загрузки всей доступной истории. Первые запросы ограничиваются
   `until` в миллисекундах; следующие передают только `cursor=next_cursor`.
5. Настроить `EVOTOR_STORE_ID`, токен и флаг в тестовом окружении. Запустить
   `node scripts/sync-evotor.mjs` из серверного окружения. Он не меняет кассу.
   Если ответ `complete:false`, повторить до `complete:true`.
6. Сверить образцы SELL/PAYBACK с обезличенной реальной схемой. Проверить суммы
   после скидок `body.result_sum`, позиции `positions[].result_sum`, платежи,
   печатные группы и fiscal results. Не включать production до такой сверки.
7. После согласованной production-активации поставить отдельную задачу worker
   `node scripts/sync-evotor.mjs` каждые 5 минут. Это предлагаемый интервал нашего
   worker, а не SLA Эвотора. Он не устанавливается этим PR. Не встраивать в prestart.

Кнопка «Загрузить из кассы» в админке читает одну страницу за запрос. Она нужна
для управляемой проверки, а регулярный worker — для полной автоматической сверки.
И «Обновить», и смена фильтра читают уже импортированные данные; не запускают API-импорт.

## Действия непосредственно в баре

1. **Касса:** сфотографировать наклейку и версию ПО. Проверить интернет и магазин,
   к которому привязана касса. Не обновлять прошивку и не сбрасывать устройство.
2. **Владелец:** в кабинете проверить приложение, его установку на кассах этого
   магазина и условия оплаты. Если установка платная — сначала согласовать цену.
3. **Сервер удалённо:** проверить токен, магазин, доверенный TLS и статус импорта.
4. **Админка Пивника:** открыть панель владельца → «Все продажи кассы». До
   полного первого прохода кассовая выручка будет недоступна, а не равна нулю.
5. Выполнить сценарии ниже на тестовом подключении с настоящими кассовыми данными.
   Изменения рабочей БД/кассы требуют отдельного разрешённого этапа.

## Первая реальная продажа: как доказать результат

1. Провести обычную покупку гостю без приложения. Сохранить бумажный чек, время,
   сумму, номер чека, фискальный номер и ФН. Не оформлять фиктивную продажу.
2. Дождаться появления документа в Облаке Эвотора. В тестовом окружении запустить
   синхронизацию, дождаться полного прохода. В «Все продажи кассы» проверить
   документ и сумму; в «Клиенты приложения» он появляться не должен.
3. Повторить загрузку: число документов и сумма не увеличиваются.
4. На отдельной покупке участника: сверить именно его бумажный чек с импортированным
   документом (время, номер чека/фискальный номер, сумма), выбрать «Связать с QR»
   в админке, отсканировать/вставить QR Пивника и подтвердить. Один документ
   разрешено связывать только с одним профилем. В БД сохраняется автор подтверждения.
5. Связанная покупка уже входит в общую выручку. Она появляется в разделе клиентов;
   общая сумма от подтверждения не меняется. Баланс бонусов тоже не меняется.
6. При наличии реального возврата: выполнить обычный кассовый возврат, импортировать
   PAYBACK; проверить, что он уменьшает итоговую выручку. Клиент наследуется только
   по явному `base_document_id` Эвотора и однозначной связи исходной продажи.
7. В тестовом worker отключить сеть/подставить невалидный тестовый токен, затем
   восстановить: ошибка видна, последняя успешная сверка сохранена; повторный
   проход не дублирует данные. Продажи возле 00:00 считать по Москве.
8. Вход клиентом/барменом: финансовые API недоступны. Роль viewer читает аналитику,
   но не запускает импорт и не подтверждает связь; admin может эти операции.

## Ограничения, которые нужно понимать до подключения

- Загрузка всех продаж не определяет покупателя автоматически. Для первого этапа
  подтверждение делает администратор через конкретный чек и QR. Для автоматического
  сценария бармена на самой кассе нужен отдельный SDK-компонент Эвотора, который
  сохраняет идентификатор клиента в контексте своего приложения (`extras`). Здесь
  он не реализован; телефон/почта чека не используются для догадок о профиле.
- Один источник + магазин + ID документа = одна строка; повторный импорт обновляет
  её. Документ может содержать несколько печатных чеков. Их число учитывается по
  `pos_print_results`; многогрупповой документ с одним клиентом не связывается.
  Если fiscal results отсутствуют, количество чеков и средний чек неизвестны.
- Возврат без явно связанного основания остаётся несвязанным. Его общая сумма
  всё равно учитывается. Удалённый/объединённый профиль не приписывается новому
  автоматически; такие связи перестают учитываться в клиентской когорте.
- История читается полной сверкой каждый проход. Это находит старые документы,
  загруженные после офлайна, и обновления. После 20 страниц worker сохраняет
  курсор и продолжает следующим запуском; HTTP-кнопка — после одной страницы.
  Отозванный курсор сбрасывается с видимой ошибкой, следующий проход идёт с начала.
- Задержка = доставка касса → облако + ожидание worker + длительность прохода.
  Фактическое время нужно измерить первой продажей; точного SLA пока нет.
- Не обещаем недоступную истории глубину. Первая загрузка читает всё, что вернёт
  API для данного токена/магазина; ограничения доступа/хранения проверяются в кабинете.
- Список последних документов ограничен 100 строками; агрегаты считают весь период.
  Товары показываются по конечным суммам позиций, платежи — в детализации источника.
  Доступны CASH/ELECTRON и дополнительные методы лишь при наличии в JSON.
- Ошибочную QR-связь нельзя незаметно переназначить. В этом этапе нет UI отмены:
  остановить подтверждения и подготовить отдельную проверяемую коррекцию с аудитом.

## Отключение без удаления данных

Остановить расписание worker, выставить `PIVNIK_POS_ENABLED=false` в серверном
окружении и worker. При необходимости отозвать токен в кабинете Эвотора. Уже
загруженные таблицы не удалять, кассу не сбрасывать. Админка покажет «Касса не
подключена». Бонусы, QR, VK/TG, колесо и kiosk продолжают работать независимо.
