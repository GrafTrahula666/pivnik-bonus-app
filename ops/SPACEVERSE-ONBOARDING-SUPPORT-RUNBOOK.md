# Обращение о проблеме подключения CRM

Это внутренняя очередь SPACEVERSE, не отправка письма/сообщения и не выдача
внешнему разработчику доступа к заведению. Статус `recorded` означает только
сохранение в панели; прочтение, начало работы и решение этим шагом не подтверждаются.

## Включение в разрешённом тестовом контуре

1. Вручную примените новую Admin migration
   `017_onboarding_support.sql` после существующих миграций. Запуск приложения
   её не применяет. Таблицы ПИВНИКА и tenant/customer runtime не меняются.
2. В тестовой конфигурации включите `ADMIN_ENABLE_ONBOARDING_SUPPORT` вместе
   с существующими writes/drafts; для обычного владельца/управляющего нужен
   invitation mode и текущие canonical grants. Новая возможность default-off.
   Этот runbook не даёт разрешения менять production env/DB.
3. Откройте сохранённый черновик с подготовленной областью. В блоке
   «Помощь с подключением» выберите причину и нажмите «Сохранить обращение».
4. Сохраните номер обращения. После reload или повторного открытия того же
   заведения список восстанавливается. Если ответ потерян, нажмите
   «Обновить обращения». Повтор той же причины сохраняет прежний номер.
5. Оператор платформы с текущей ролью SUPER_ADMIN видит очередь на странице
   «Платформа», может обновить её и открыть следующие 25 записей. Чтение
   очереди аудируется. Бизнес-владелец/управляющий эту общую очередь не видит.

## Реальный серверный контракт

- `GET /api/admin/onboarding/drafts/:draftId/support` — текущие обращения
  разрешённого черновика. Доступ только владельцу/управляющему с write grant;
  viewer, отозванный доступ, чужая точка и другая компания не допускаются.
- `POST` по тому же адресу принимает **только**
  `{"topic":"connection"}`. Другие темы: `customer_data`, `access`, `activation`.
  Один `draftId + topic` — одно обращение; PostgreSQL lock/unique constraint
  обеспечивают конкурентный повтор. Произвольные scope/status/text/keys
  запрещены. Origin, CSRF, действующая сессия и actor rate limit обязательны.
- Ответ: `schemaVersion:1`, серверные `draftId` и `scope`,
  `delivery:"internal_queue"`, `externalNotificationSent:false`, `requests`.
  Каждая запись содержит `id`, `draftId`, `topic`, `status:"recorded"`, `createdAt`.
  Идентификатор формирует сервер. Только четыре фиксированные темы, без
  свободного текста, контактных данных, клиентских данных, URL, секретов или
  скопированных ошибок провайдера. Не отправляйте ключи в обращения.
- `GET /api/admin/onboarding/support?offset=0` — очередь только SUPER_ADMIN,
  до 25 записей, `nextOffset`; query scope/повторные параметры запрещены.
  Доступ к очереди не предоставляет прав на CRM клиентов или настройки точки.
- Запись обращения и tenant-scoped audit атомарны. Ошибка аудита откатывает
  запись; отсутствие миграции возвращает 503, не пустой список и не успех.
  Неуспешный audit чтения общей очереди также не выдаёт данные.

## Границы этой итерации

Нет внешних уведомлений, SLA, назначения исполнителя, переписки, разрешения
обращений, доступа внешнего разработчика или автоматического исправления
подключения. Лицензия/CRM/касса не активируются. При выключенном флаге старое
локальное копирование обращения в списке заведений продолжает работать.
Оператору видны ID подключения/компании/точки и причина; свободный текст
владелец по-прежнему может передать выбранным им способом через прежнее
копирование. Это не входит в сохранённую очередь и не отправляется из панели.

Тесты: `server/tests/onboarding-support.spec.ts` (signed HTTP, SQL, native
PostgreSQL concurrency при opt-in); built desktop/mobile:
`SPACEVERSE_E2E_SUPPORT=true npx playwright test -c playwright.tenant-crm.config.ts`
с существующим синтетическим native PostgreSQL fixture. Никакие production
адреса/credentials или реальные кассы в проверках не используются.
