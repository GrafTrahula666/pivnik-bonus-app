## 2. Предлагаемое продуктовое решение (требует согласования владельца)

1. **Каналы первой версии:** Telegram и VK по отдельности. `all` только пользовательский выбор двух независимых каналов. Email, SMS, web push и рекламные кабинеты — вне 121.
2. **Разделить цели:** сервисные/транзакционные уведомления не являются маркетинговыми. Согласие на общие правила, вход в приложение, наличие Telegram/VK identity, факт покупки и отсутствие отписки **не** являются доказательством согласия на промо.
3. **Fail closed:** для конкретной пары tenant + клиент + канал + цель `marketing` разрешать отправку только при действующем, доказуемом, явно предоставленном согласии. Отсутствует, неизвестно, истекла применимость, отозвано, не соответствует текущей identity или версия текста невалидна: **не отправлять**.
4. **Раздельная воля:** включение Telegram не включает VK, и наоборот. Отзыв в одном канале немедленно блокирует новые маркетинговые отправки по нему, без влияния на другой канал.
5. **Legacy:** существующие `marketing_opt_in`/`terms_accepted_at` нельзя автоматически конвертировать в согласия на оба канала. До согласованной миграции новые SaaS-кампании не должны использовать старый фильтр, а legacy-поведение и его возможная остановка требуют отдельного решения владельца и проверки воздействия. Никакой массовой записи или ретроспективного выдумывания доказательств.

## 3. Минимальный будущий контракт доказательства

Append-only событие `marketing_consent_events` (логическая схема; SQL ещё **нет**):
- `event_id`, `tenant_id`, `customer_id`, `channel` (telegram/vk), `purpose` (marketing), `action` (grant/revoke);
- `consent_text_version` и `consent_text_sha256` (оба для grant обязательны), `source_surface` / `platform`, `server_occurred_at`, `request_id` и `idempotency_key`;
- ссылка на проверенную связанную provider identity (через собственный ID, без записи токенов/секретов), источник аутентификации, actor/customer, версия доказательства согласия.

Оперативное состояние следует выводить из последнего валидного события (или поддерживать transactional projection с привязкой к event_id). Никаких клиентских timestamp как единственного доказательства. Запретить подмену tenant/customer/channel из тела запроса: сервер извлекает scope из проверенной сессии и канонических связей. Повтор запроса должен быть идемпотентным; аудит не содержит токенов, тела личного сообщения и лишних персональных данных.

## 4. Контроль отправки, границы и инварианты

- Проверять права actor, tenant и venue на сервере; отбирать аудиторию **только своего** tenant. Отдельный отрицательный тест: tenant A не получает recipient tenant B даже по прямому ID.
- Проверять конкретный канал, активную identity и актуальное согласие при построении preview **и повторно перед отправкой каждому получателю**. Отзыв между preview и отправкой запрещает отправку.
- Удалённые/объединённые клиенты, невалидные identity, отсутствие подтверждения согласия = исключить с прозрачной причиной, не считать «нет данных» как true.
- Сохранить существующий 10-минутный broadcast dedupe, таймаут Telegram, ограничения отправки и действующие `Do not break`. Доставка подтверждается отдельно (CHAT 13 / 124), не выводится из факта попытки.
- UI (отдельный будущий этап): два независимых выключенных по умолчанию переключателя с ясным текстом, ссылкой на условия, явным подтверждением backend, доступной немедленной отпиской и понятными состояниями loading/error/disabled на mobile.
