# Подключение заведения SPACEVERSE

Рабочая часть в Draft PR #273: приглашение → вход → сохранённый мастер →
подготовленная выключенная точка. Доступ к документам Эвотора
можно проверить отдельно; это не подтверждает связь терминала или развёртывание.
Подготовленное заведение нельзя считать активным.

## Для владельца

1. Войдите в Business под владельцем своей организации. Откройте «Приглашения».
2. Выберите организацию или уже подготовленную в мастере точку, роль и срок
   (1–168 часов). Нажмите «Создать приглашение» и передайте ссылку управляющему.
   Код `SVI-…` также можно вставить через «Войти по приглашению».
3. Управляющий открывает ссылку и создаёт учётную запись либо входит в свою
   существующую. Пароль существующей учётной записи приглашение не меняет.
4. В мастере управляющий выбирает разрешённую организацию, заполняет заведение,
   сохраняет черновик и настройки приложения. После перезагрузки сохранённый
   черновик снова доступен. Приглашение на точку открывает именно её черновик.
5. «Подготовить область» резервирует выключенную точку. Статус «Не запускалась»
   означает, что приложение, база и связь с кассой ещё не развёрнуты. Ожидайте
   следующих шагов мастера; этот статус не подтверждает готовность заведения.
6. Если серверная подготовка разрешена, блок «База приложения» читает сохранённое
   состояние и запускает только точную привязку заранее подготовленной выделенной
   базы. При статусе «Нужно действие» выполните указанное инфраструктурное действие
   и повторите шаг. Строка подключения в браузере не вводится. Даже статус
   «Привязка подготовлена» не запускает runtime и не публикует приложение.
7. После привязки запустите «Проверить схему». Проверка только читает выделенную
   БД и подтверждает ручные миграции и exact ownership. При требовании миграции
   или разбора исторических строк обратитесь к инфраструктурному оператору:
   мастер не применяет SQL и не присваивает существующих клиентов автоматически.
   «Схема готова» всё ещё не означает запуск или публикацию приложения.
8. После готовой схемы запустите «Собрать и проверить bundle». Сервер использует
   только сохранённый manifest и общий контракт существующего приложения;
   manifest, artifact path, URL базы и credentials в браузере не вводятся.
   Успех подтверждает checksum конфигурации, текущие утверждённые файлы и
   зарегистрированный immutable image ID с ожидаемыми source/config. Отсутствие
   регистрации файлов или образа показывает отдельную причину «Нужно действие».
   Запуск runtime и публикация приложения проверяются отдельно и пока закрыты.
9. В «Шагах подключения» выберите, откуда продолжить, укажите ID/название
   терминала и выбор кассовых отчётов. «Сохранить прогресс» сохраняет это на
   сервере; после перезагрузки выбор восстановится. Лояльность и магазин берутся
   из уже сохранённого приложения. ID терминала не является ключом устройства.

«Подтверждено» у провайдера означает подтверждённое чтение его документов.
Терминал, развёртывание и итоговая связь имеют отдельные статусы. Пока связь
не подтверждена, отчёт недоступен и сумма неизвестна; это не нулевая выручка.

Ссылка одноразовая. Повторное принятие разрешено только той же вошедшей учётной
записи для восстановления ответа. Истёкшую ссылку нужно заменить. «Отозвать»
отзывает ссылку и выданные ею права, даже если управляющий уже вошёл. Другие
независимо выданные права этой учётной записи остаются в своих областях.
Просмотрщик видит разрешённый черновик без кнопок записи. При отсутствии ответа
повторяйте исходную команду: новая команда не нужна для восстановления результата.

В «Заведениях» видно все доступные точки: сохранённые для подключения и уже
созданные ранее. «Продолжить подключение» открывает сохранённый мастер нужной
точки. Список показывает причину, требующую внимания, и отдельно время последнего
события устройства и изменения настройки. «Показать ещё заведения» раскрывает
следующую страницу. Сама запись active в metadata не подтверждает связь старой
точки: без проверки она остаётся «Ожидает подключения» с неизвестной суммой.

«Нужна помощь разработчика?» готовит текст обращения из вашего описания и
состояния подключения. Скопируйте его и передайте своему разработчику; сообщений
и заявок вне панели этот шаг не отправляет. В диагностике нет сохранённых ключей
или кодов приглашения. Подключение стороннего мобильного приложения будет
отдельным Mobile Integration Hub с ограниченным приглашением разработчика;
сейчас такой доступ и автоматическое подключение закрытого приложения не выдаются.

## Подготовка тестовой среды

Миграции применяются только вручную в разрешённую тестовую БД, без сброса схемы.
Admin metadata требует последовательность `admin-migrations/001`–`015`.
Приглашения требуют `ADMIN_ENABLE_WRITES=true`,
`ADMIN_ENABLE_ONBOARDING_DRAFTS=true`, `ADMIN_ENABLE_ONBOARDING_INVITATIONS=true`
и уже настроенный `ADMIN_CSRF_SECRET` длиной не менее 32 символов. Для этой
итерации реальные Railway variables/secrets не менялись; флаги по умолчанию выключены.
Сохранение и показ статусов шагов также требует `ADMIN_ENABLE_ONBOARDING_WORKFLOW=true`.

Для прокси v2 отдельно нужен `ADMIN_ENABLE_ONBOARDING_POS_PROXY=true`.
В разрешённой тестовой tenant БД вручную применяются POS 012/013, binding 017–019
и новая 021. Admin сохраняет ключ устройства зашифрованным существующим keyring.
Адрес выбирается по `ADMIN_ONBOARDING_PROXY_REGISTRY_JSON`: runtime key → имя
`SPACEVERSE_TENANT_PROXY_ORIGIN_*` переменной с HTTPS origin. Браузер не передаёт
адрес, runtime или область. Это процедура настройки тестовой среды, не разрешение
на изменение реальных env/secrets, касс или БД.

В мастере сохраните ID терминала, магазин прокси и `X-Pivnik-Device-Key`.
Отправьте с разрешённого тестового терминала
`POST /api/device/pos/onboarding/event` с тем же заголовком и JSON
`{"eventId":"<новый UUID v4>","kind":"onboarding_test"}`. Повтор того же UUID
возвращает исходную квитанцию и не обновляет время активности. Затем нажмите
«Проверить связь»: Admin только читает
`GET /api/device/pos/onboarding/status?challenge=<UUID v4>`, сам события не создаёт.
Ответ должен подтвердить runtime/точку/устройство, nonce и MAC. Для готовности
связи требуется событие не старше 5 минут и полная загрузка документов провайдера
не старше 15 минут. Статус возвращается с объяснением и следующим действием.
Без регистрации прокси — pending; отсутствующее событие и незавершённая загрузка
показываются отдельно. Отозванный ключ и подменённый ответ не проходят проверку.

Пустой подтверждённый период (последние 24 часа до полного sync) показывает
«0 ₽ · 0 чеков · данные получены». При отсутствии связи сумма неизвестна.
Непустой отчёт подтверждает наличие данных, но не раскрывает суммы/клиентов по
device key; подробности должны читаться отдельными авторизованными отчётами.
Даже успешная проверка связи не означает, что приложение развёрнуто или точка
активна. Tenant startup guard остаётся закрытым; реальные внешние действия не
выполняются в этой итерации. Desktop/mobile E2E использует native HTTP handler
и синтетические SQL/device/provider fixtures, а не реальные кассы.

Tenant runtime использует прежнюю canonical модель и ручные root migrations
009 и 017–020 (актуальная 020: `spaceverse_customer_create_requests`). Его запуск
по-прежнему блокируется `SPACEVERSE_RUNTIME_NOT_PROVISIONED`.
Provisioning в тестовой среде отдельно требует
`ADMIN_ENABLE_ONBOARDING_PROVISIONING=true`, строгую карту
`ADMIN_ONBOARDING_DATABASE_REGISTRY_JSON` из runtime key в имя защищённой
`SPACEVERSE_TENANT_DATABASE_URL_*` переменной и вручную применённые 017/018 в
целевой базе до binding. Для успешной read-only проверки должны быть
вручную применены 009 и 017–020, а все существующие users/identities/wallets/
transactions/create-request rows должны иметь exact ownership этой точки.
Исторические строки нельзя автоматически присваивать новому tenant. URL, host
и credential не передаются мастеру или его API. Runtime bundle собирается
после этой проверки из того же frozen manifest; отдельный browser input или
секрет для него не требуется.
Не запускайте prestart/materialize ради применения новых миграций и не обходите
guard для проверки реальных устройств. Browser E2E использует синтетическую SQL
fixture: `cd admin-platform && npm run test:e2e:onboarding`; сценарий приглашений
запускается отдельно через `npm run test:e2e:invitations`.

Проверка runtime bundle теперь требует утверждённую версию серверных модулей.
Прежний успешный JSON descriptor не заменяет эту проверку: мастер предложит
повторить тот же шаг. Отсутствующая регистрация или изменённые файлы показываются
как «Нужно действие», приложение остаётся not_provisioned.

Для разрешённой локальной тестовой сборки оператор явно создаёт новый файл:
`node scripts/build-spaceverse-runtime-release.mjs --source-sha <текущий git HEAD SHA> --output <новый файл>`.
Скрипт проверяет HEAD и сохраняет SHA256 фактических серверных модулей и их
literal relative imports, включая package.json/lock. Source SHA обозначает
базовый git commit; fingerprint фиксирует фактические байты, в том числе
результат materialize. Обе величины проверяются против отдельного утверждения
оператора. Не регистрируйте автоматически пересчитанный hash как утверждённый.
В тестовом процессе задаются только non-secret ссылки `ADMIN_RUNTIME_RELEASE_SHA`,
`ADMIN_RUNTIME_RELEASE_FINGERPRINT`, `ADMIN_RUNTIME_RELEASE_MANIFEST_FILE`.
Браузер их не выбирает и не передаёт. В этой итерации реальные Railway
variables не меняются. Покрытие не является проверкой полноценного Docker image,
frontend assets или вычисляемых импортов; следующий шаг — конкретный immutable
image и разрешённый возобновляемый запуск. Сервис этим скриптом не стартует.

Для локального образа существует отдельный build-only путь:

1. `node scripts/prepare-spaceverse-runtime-image.mjs --output /tmp/sv-image-context`
   создаёт новый allowlisted контекст и повторно проверяет скопированные модули.
   `.git`, `.env`, `.npmrc`, Business, tests и host `node_modules` не копируются.
   Повтор с тем же каталогом отвергается, существующие файлы не перезаписываются.
2. В этом временном контексте выполните
   `npm ci --omit=dev --ignore-scripts --cache /tmp/sv-image-npm-cache`.
   Это заполнение публичного кеша по lockfile, без lifecycle scripts. Сборка
   заново устанавливает dependencies внутри образа; host node_modules исключён.
3. Используя SHA/fingerprint из созданного release record, выполните
   `docker build --build-context npm-cache=/tmp/sv-image-npm-cache --build-arg SOURCE_RELEASE_SHA=<SHA из record> --build-arg SOURCE_RELEASE_FINGERPRINT=<fingerprint из record> -t spaceverse-runtime-candidate:local /tmp/sv-image-context`.
   Node base закреплён digest, npm install внутри Docker работает offline с
   проверкой lockfile integrity. Кеш и логи находятся в tmpfs; proxy, CA и
   credentials в образ не включаются. Tag служит только локальной меткой.
4. Получите `docker image inspect spaceverse-runtime-candidate:local` и
   проверьте его через `verifyRuntimeImageInspection` с независимо утверждённым
   `sha256:…` image ID и code proof. Mutable tag, другой digest/source,
   root user, legacy entrypoint, неверный режим и неизвестные baked env запрещены.

Идентичность локального Docker image не является registry digest или доказательством
публикации. Образ запускается пользователем `node` через отдельный tenant wrapper,
без npm prestart, автоприменения миграций или legacy fallback. Wrapper перепроверяет
bundle v2 и фактические модули, затем сохраняет прежний запрет старта. Даже
валидный образ остаётся `not_provisioned`: разрешённый runner, activation и
terminal provisioning ещё не реализованы.
Не используйте эту инструкцию как разрешение на deploy или изменение Railway.

В тестовом Admin процессе регистрация образа использует non-secret operator-only
`ADMIN_RUNTIME_IMAGE_ID` и `ADMIN_RUNTIME_IMAGE_INSPECTION_FILE` вместе с прежними
SHA/fingerprint/file references. Inspection file должен быть регулярным JSON до
80 KB без symlink; ожидается независимо утверждённый immutable ID, не tag. Сервер
повторно проверяет текущие модули и сравнивает image ID/platform/config/source
labels. Inspection metadata — свидетельство о зарегистрированном локальном
артефакте, а не ответ живого сервиса. Browser не выбирает ID, путь или metadata.
В этой работе Railway env не меняются, image не публикуется.

Bundle v3 включает image ID/platform/contract в общий digest вместе с code proof
и exact manifest scope. v1/v2 остаются читаемыми, но production verifier требует
v3: прежний ledger success без image proof виден как «Нужно действие» и повторяется
в той же записи с новым attempt. GET состояние не меняет. Отсутствующая
регистрация, другой ID/source/config возвращают безопасную конкретную причину.
Даже проверенный v3 остаётся not_provisioned/published=false/startAllowed=false;
мастер явно отделяет «файлы проверены», «образ проверен» и будущий запуск.

При включённом новом flag старые ссылки `/invite/…` требуют перевыдачи в
«Приглашениях». Их записи и ранее выданные независимые права сохраняются.
Новая migration 011 расширяет существующую таблицу 007/008, без второй модели.

Ключи провайдера/терминала, строки подключения и коды приглашений нельзя писать
в audit, draft JSON, runtime manifest или browser storage. В браузере ссылка
показывается только владельцу по явному запросу и получателю из её fragment.
