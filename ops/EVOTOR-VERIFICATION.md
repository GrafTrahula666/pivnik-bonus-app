### POS-сценарии

12 новых тестов проверяют точные копейки и дробное количество, анонимную продажу,
закрытые документы и магазин, повторный импорт/обновление без дублей, возврат по
явному основанию, ручную QR-связь и конфликт перепривязки. Дополнительно проверены
отозванный QR, отказ связать несколько чеков с одним клиентом, удалённый профиль,
повторный покупатель, границы московского дня, откат ошибочной страницы,
продолжение по сохранённому курсору и поздний документ после офлайна.

Проверены API V2-заголовки, курсор без повторения фильтров, 401/402/403/429 и
сетевая ошибка без раскрытия секрета. Просроченный токен сохраняет последнюю
успешную сверку; отозванный курсор безопасно запускает новый полный проход.
Реальный HTTP gateway отдаёт новые ассеты для TG/VK и отвечает 401 на все три
финансовых маршрута без входа. Общий сервис допускает чтение admin/viewer и запись
только admin; до первой полной сверки возвращает отсутствие кассовых метрик.

SQL-сценарии используют изолированную PGlite (PostgreSQL/WASM), а API — фикстуры.
PGlite не поддерживает advisory locks: в адаптере тестов заменены только вызовы
lock/unlock; остальные SQL-запросы настоящие. Межпроцессную блокировку нужно
дополнительно проверить на тестовом сервере PostgreSQL при подключении.
Никаких начислений/списаний бонусов импорт не делает; отдельный тест проверяет
отсутствие записей в журнале транзакций.

### Отдельный блокер зависимостей

Полный аудит сообщает о `qs` и его потребителях `body-parser`/`express`:

- [GHSA-x5fp-wj9c-mxmx — array-limit bypass](https://github.com/advisories/GHSA-x5fp-wj9c-mxmx)
- [GHSA-4mjr-xmp4-gh2g — isBuffer denial of service](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g)

Lockfile побайтово совпадает с исходным `origin/main`; зависимости этой задачей
не добавлялись и не обновлялись. Исправление требует отдельной задачи, как
предписывают инструкции проекта. Это три уязвимых пакета и две связанные
рекомендации, а не три независимые найденные ошибки в новом POS-коде.
Следовательно, нельзя называть весь полный audit зелёным или обещать готовность
к production. Существующий CI использует порог high и может быть зелёным при
этом отдельном красном полном аудите.

## Что ещё требует реального подключения

Нет проверенного токена/ID магазина, обезличенных реальных SELL/PAYBACK,
подтверждённой модели/версии кассового ПО и условий API конкретного владельца.
Поэтому реальный импорт, срок доставки в облако и приёмочный сценарий первой
продажи пока не проверены. Автоматическая идентификация покупателя на кассе
отдельным SDK-компонентом не реализована; текущий этап использует подтверждение
администратором по конкретному чеку и QR.

Флаг выключен по умолчанию. Миграция только подготовлена и не входит в
автоматический startup; расписание worker не установлено. Merge, production-деплой,
изменения рабочей БД/кассы, покупка подписок и настройка кабинетов не выполнялись.
Draft PR предназначен для ревью кода; активация — отдельный согласованный этап.
