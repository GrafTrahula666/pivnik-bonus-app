# PIVNIK Halloween Live

Отдельный сервис мероприятия 31 октября 2026 года. Существующий Mini App,
CRM, киоск, кассовые маршруты и patch-chain не изменяются. Этот каталог не
подключён к их startup, CI deploy или миграционной allowlist.

`/scanner` — устанавливаемый сканер iPhone, `/control` — пульт,
`/screen` — телевизор. Electron открывает пульт и независимое окно шоу в одной
сохранённой сессии. Сканер не содержит действий жеребьёвки.

## Демо: начать за несколько минут

Требуется Node.js 20+ и весь репозиторий: используются его неизменённые
`qr-resolver.js`, `platform-core.js`, `halloween-raffle.js` и миграция 011.

```sh
cd halloween-live
npm ci
npm run build
npm run demo
```

Открыть `http://localhost:4317/control`. При первом запуске уникальные коды
входа сохраняются в `.data/demo-access.txt` с правами 0600. Учётные записи:
`owner`, `scanner`, `screen`. Не публиковать файл доступа.

В демо `/scanner` открывается сразу без логина и пароля. Доступ ограничен
регистрацией гостей; пульт и главный розыгрыш остаются под авторизацией.
В режиме live вход сканера по-прежнему требует учётную запись.

Вымышленные гости: `PVK-DEMO-0001` … `PVK-DEMO-0016`. На пульте нажать
«Добавить по коду» либо в сканере «Ввести код». Затем выбрать приз,
«Начать локальный розыгрыш», подтвердить, отдельно раскрыть победителя.
Данные сохраняются в `.data/demo`; перезапуск их не сбрасывает.
Демо никак не подключается к настоящей БД, наградам или финансам.

### Запуск одним файлом в Windows

После первого `npm ci` и `npm run build` можно запускать файл `START-DEMO.bat`
двойным щелчком. Он сам поднимает временный HTTPS-адрес Pinggy, запускает демо
и печатает три адреса: `/control`, `/scanner`, `/screen`. Окно оставляют открытым
весь вечер. Ссылка Pinggy бесплатного режима временная (около часа); при новом
запуске адрес меняется. Пароли остаются в `.data/demo-access.txt`.

Если Windows спросит подтверждение SSH, введите `yes`. Скрипт использует только
локальный порт 4317 и не меняет основной проект.

Главный демо-сценарий: «Закрыть демо-билеты» → «Провести жеребьёвку» →
пять рамок → III → II → I. Изменение demo closes_at возможно только в
изолированной embedded-БД и отсутствует в настоящих правах роли.

## Windows 11

Установщик: `PIVNIK-Halloween-Setup.exe`. Обычный NSIS-мастер, выбор каталога,
ярлыки на рабочем столе и в меню «Пуск», отдельная иконка. Это Electron-программа;
внешний браузер для работы пульта не нужен. Сервер и база в установщик не входят.

После установки указать **HTTPS origin** сервера без пути, затем войти.
`Ctrl+Shift+B` открывает смену адреса. «Экран шоу» позволяет выбрать монитор.
Беспроводной дисплей сначала подключить в Windows через Win+K, выбрать
«Расширить» через Win+P; программа увидит его как обычный монитор.
Окно шоу и сессия восстанавливаются после перезапуска.

Для локального демонстрационного сервера разрешён явный режим:
в PowerShell установить `$env:PIVNIK_DESKTOP_DEMO='1'` и запустить программу,
затем указать `http://localhost:4317`. Это не разрешает произвольные HTTP-серверы.

Сборка исходников:

```sh
npm run dist:win
```

Результат в `release/PIVNIK-Halloween-Setup.exe`, Windows x64. На Linux
используется NSIS-мастер с обычным WriteUninstaller, без выполнения Windows-кода
во время сборки. Удаление использует точный список установленных файлов. Подпись Authenticode
не настроена. Фактическая установка на Windows 11, Miracast и второй физический
монитор требуют отдельной проверки на соответствующем устройстве.

## Настоящие пользователи и билеты

**Production-миграции, deploy и изменение closes_at в рамках разработки не выполнялись.**
Доступ к настоящей БД и её текущее состояние не подтверждены.
До подключения оператор проверяет резервную копию, существование миграции 011,
каноническую строку `night-of-cauldrons`, установленное closes_at и состояние
главного розыгрыша. В исходной 011 указан 31.10.2026 20:00 МСК; это не доказывает
production-значение. Изменять его на 30 октября автоматически запрещено.

После отдельного разрешения администратор БД вручную применяет
`migrations/001_live.sql`, `002_event.sql`, проверяет `003_grants.example.sql`
и выдаёт отдельной роли только перечисленные права. Сервис при старте
никогда не создаёт/мигрирует настоящие таблицы и не подменяет ошибки демо-данными.

Используется **та же БД**, что у существующего PIVNIK; новые данные лежат в
`halloween_live`. Нет копии/собственного баланса билетов. QR проверяются
`resolvePersonalQrRecord`, включая URL/JSON, короткие коды и merge aliases;
отозванные self-aliases исключены. Перед локальным snapshot перепроверяется
каноническая личность зарегистрированных гостей, чтобы merge не давал второй шанс.

Закрытие настоящего набора вызывает существующий `closeDraw` без `force` и
без изменения срока. Главная жеребьёвка вызывает существующий `drawNight`.
Её блокировка, seed, hash и результаты остаются в **канонической** `halloween_draw`;
новый сервис сохраняет ссылку/доказательства и состояние раскрытия в своей схеме.
Уже проведённый канонический розыгрыш импортируется после проверки seed/snapshot,
а не разыгрывается заново. Нет второго источника истины для главных результатов.

Настройка окружения:

```sh
# Создать приватный .env по .env.example и заполнить локально.
# Пароль передавать через stdin, не аргументами процесса:
npm run password
# Ввести уникальный пароль не короче 16 символов и завершить stdin.
node --env-file=.env src/server.js
```

`LIVE_ACCOUNTS_JSON` содержит массив `{ "name": "...", "role": "owner",
"passwordHash": "salt:hash" }`. Роли: owner — всё; operator — локальные
розыгрыши/призы/раскрытие/отчёты; scanner — регистрация и подтверждаемое удаление;
screen — только уже раскрытое шоу. У каждого свой пароль. Сессии — случайные
256-битные, в БД хранится SHA-256; cookie HttpOnly, Secure, SameSite=Strict,
срок 12 часов. Смена пароля/роли отзывает ранее выданные сессии.

`LIVE_DATABASE_URL` должен указывать на выделенную роль с проверкой TLS-сертификата
по правилам провайдера. Не использовать общие superuser/service credentials.
Настоящие `users`, `wallets`, `transactions`, `beer_loyalty`, билеты и кассовые
таблицы новая роль изменять не может. На `halloween_draw` выдаются только пять
необходимых UPDATE-колонок; права на `closes_at` нет.

HTTPS reverse proxy передаёт все три интерфейса на отдельный процесс 4317,
сохраняет Origin/Host, отключает buffering у `/api/events`, выставляет idle timeout
не меньше минуты. `LIVE_PUBLIC_ORIGIN` должен точно совпадать с адресом пользователя.
`LIVE_TRUST_PROXY=1` допустим только за одним доверенным proxy с закрытым backend.
Cookies не разделяются с основным приложением: использовать отдельный hostname.

На iPhone открыть **HTTPS** `/scanner` в Safari → Поделиться → На экран «Домой».
Разрешить камеру. Используется задняя камера и ZXing, поэтому BarcodeDetector не
требуется. Фонарик, вибрация и звук зависят от браузера/устройства. При отказе
камеры доступен ручной код. Service worker кэширует только оболочку; API,
гости, пароли и QR в кэш или offline-очередь не записываются.

## Честность, повторные запросы и выдача

Каждый гость локального snapshot имеет ровно одну позицию. Выбор — серверный
`crypto.randomInt(pool.length)` без modulo bias. Snapshot, hash, победитель,
оператор и правило исключения сохраняются одной транзакцией. По умолчанию
повторные локальные победители исключены; правило нельзя менять после первого
розыгрыша. Поздние регистрации попадают в последующий snapshot.

Повторный draw блокируется до раскрытия текущего. Перевыбор разрешён только
для отсутствующего победителя, с основанием и сохранённым parentId. Первоначальные
результаты не изменяются. Повторная выдача окончательно вручённой награды запрещена.

`Idempotency-Key` обязателен, связан с действием, оператором и SHA-256 параметров.
Полные параметры QR не сохраняются. Event row lock сериализует изменения между
процессами. Audit append-only по SQL grants, содержит связанный SHA-256 chain.
Цепочка обнаруживает изменение строк при неизменённом хвосте; против администратора
БД, способного переписать всю историю, нужны внешние копии/закрепление hash.

Денежных SQL-записей в сервисе нет. Локальные bonus-призы могут выдаваться через
опциональный server-only bridge к **существующему** защищённому
`POST /api/admin/users/:id/adjust`. Он выключен по умолчанию. Включать только после
проверки правильного HTTPS origin и отдельной действующей admin-сессии.
Ключ операции `halloween-live:<event>:<draw>` постоянный даже после сбоя между
внешним COMMIT и нашим ответом; повтор использует существующую дедупликацию API.
Ошибка/нет bridge оставляет награду в ожидании. В демо bridge не вызывается.

Физическое пиво/кружка/произвольный приз отмечаются вручёнными с комментарием.
Существующий `/api/staff/beer-gift` **списывает накопленные подарочные литры**;
вызывать его для бесплатного приза Halloween было бы неверно. Автоматическое
списание складского пива, выдача депозитов и профильных рамок здесь не включены;
они требуют подтверждённой операции существующей системы. Не имитировать их
прямыми записями в финансовые/кассовые таблицы.

## Восстановление и проверки

```sh
npm test
npm run check
npm audit
HALLOWEEN_TEST_DATABASE_URL=postgresql://.../halloween_fixture npm test
```

Native PostgreSQL-тест запускается только с отдельной переменной и БД с именем
`halloween_fixture*`; внутри неё он пересоздаёт fixture-таблицы. Никогда не
подставлять production-URL. По умолчанию этот тест явно skipped; PGlite-сценарии
выполняются всегда. Browser smoke scripts требуют локальное запущенное демо,
системный Chromium и для camera-smoke — ffmpeg. Они используют только DEMO-коды.
`webkit-smoke.mjs` и `electron-smoke.mjs` поднимают собственное демо; нужны
соответствующие browser binaries / Linux Electron и, для desktop-проверки, Xvfb.

SSE синхронизирует интерфейсы с задержкой около секунды, включая несколько
backend-процессов через чтение общего durable состояния. Экран после перезагрузки
восстанавливает сохранённую сцену и её время; завершённый результат не переигрывается.
При потере соединения индикатор становится красным. Регистрация подтверждается
только после серверного COMMIT. Декоративная последовательность номеров фиксированная,
она не выбирает победителя. Облегчённая графика и reduced-motion поддержаны.

Ограничения компактной версии: один бар/вечер, до 40 SSE-экранов, гостевой список
и история в одной JSONB-строке. Подходит для мероприятия, не для многоплощадочной CRM.
Резервировать всю схему и канонические таблицы розыгрыша согласованным snapshot;
запускать один процесс на одну embedded demo-БД. В live разрешено несколько
процессов с общей PostgreSQL-БД. Не удалять `.data/demo` для «перезапуска» вечера.

Фактические результаты сессии, Windows build и непроверенные устройства:
`VALIDATION.md`.
