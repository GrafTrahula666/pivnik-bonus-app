# Минимальный backend‑контракт для кассы Эвотор (НЕ реализован)

Документ только описывает, что нужно от PIVNIK backend. Production‑код, БД и deploy не
менялись. Реализация — отдельной задачей после проверки прототипа на кассе.

## Почему существующего API недостаточно

`POST /api/staff/qr/resolve` уже делает нужное (QR → профиль), но требует Bearer‑сессию
сотрудника: роль staff/admin, `termsAccepted`, привязку к Telegram/VK‑идентичности,
TTL 7 дней. У автономной кассы нет человека, который логинится; сессия киоска не проходит
`requireGatewayUser`. Device‑auth из `origin/feature/kiosk-shifts`
(`/api/device/pair|bootstrap|session`) не в main и подключается через runtime‑патч
`apply-*.mjs` — использовать нельзя.

## 1. Учётка устройства (POS)

Переиспользовать модель pairing‑кода, как в kiosk device‑auth, но отдельной ролью `pos`:

- `POST /api/admin/devices/pairing-code` (админ) → одноразовый код, короткий TTL.
- `POST /api/device/pos/pair {code, evotorStoreId, evotorDeviceId}` → `{deviceToken}`;
  токен хранится на сервере только хэшем, отзывается админом.
- Права токена: **только** резолв QR. Никаких начислений, профилей, денег.

## 2. Резолв QR для кассы

```
POST /api/device/pos/qr/resolve
Authorization: Device <deviceToken>
{"payload": "PIVNIK:<qr_token>" | "PVK-XXXX-XXXX"}

200 {"pivnikUserId": "123", "displayName": "Кирилл"}
404 {"error": "not_found"}     — неизвестный/отозванный QR
401/403                        — токен устройства неверен/отозван
429                            — rate limit (на устройство)
```

- Внутри — тот же `resolvePersonalQrRecord`, без дублирования логики.
- Ответ минимальный: id и имя для индикатора, без телефона и баланса.
- Опционально позже: серверно‑подписанная одноразовая ссылка `ref` вместо голого id в extra,
  если потребуется защищаться от подделки extra третьими приложениями на кассе.

Касса уже обрабатывает ровно эти коды (`core/ResolveResult.java`); при переходе меняются только
путь и заголовок авторизации в `PivnikApi.java`.

## 3. Импорт чеков (ветка `feat/evotor-sales-dashboards-20261002`)

- Нормализатор `pos/evotor-document.js` сейчас отбрасывает extras. Нужно читать
  `pivnik_user_id` из extras **закрытого SELL‑документа облака** (точный путь и формат
  ключа — по реальному обезличенному JSON после проверки на кассе).
- `pivnik_user_id` записывать в существующую `pos_customer_links` (один документ ↔ один
  профиль) как источник `sdk_extra`; ручная привязка админа остаётся.
- PAYBACK наследует клиента только через `base_document_id` и **уменьшает**, а не начисляет.
- Идемпотентность — по id документа Эвотора (повторная доставка не создаёт второй связи и не
  начисляет повторно).
- Проверка, что `pivnik_user_id` существует и не заблокирован; иначе документ импортируется
  без клиента.

## 4. Начисление бонусов

Вне этого контракта. Только по подтверждённому закрытому документу, сумма — из документа,
никогда из QR или из данных кассового приложения.
